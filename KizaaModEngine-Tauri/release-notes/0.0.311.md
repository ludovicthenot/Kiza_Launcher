Kiza Launcher 0.0.311

Windows notifications work again, the settings pages stop freezing for a reason
the last attempt did not reach, and a mod's catalogue is now something you
recognise rather than something you read.

## Fixed

**Windows notifications appear again.** A Windows notification is not addressed
to a running program — it is addressed to an identifier Windows must already
know, and anything sent under one it cannot resolve is discarded before it is
drawn. No error is raised. The installer that replaced the old bundle wrote a
perfectly good Start menu shortcut without that identifier on it, so every
switch on the Notifications page read "on", every call reported success, and
nothing ever appeared. Kiza now claims its identifier at startup and repairs the
shortcut in place, so an install that predates this fix starts working the next
time it opens rather than needing to be reinstalled. If there is no Start menu
shortcut at all, the Notifications page says so instead of leaving you to
suspect Focus Assist.

**The settings pages no longer freeze.** The previous release added a debounce,
which made the freeze less frequent without touching what caused it. A launcher
command declared without `async` runs on the thread that draws the window: on
Windows that is the same thread that pumps the message loop, so reading the
settings file, writing it, or asking the credential store about a saved key
stopped the window from repainting for as long as the disk took to answer.
Every command the settings dialogue calls now runs off that thread, and a test
fails the build if one of them ever quietly loses the keyword again.

Three more things were making the same dialogue slower than it needed to be. The
Notifications page rebuilt every row on the page each time one switch moved,
because the row was defined inside the page and React had no way to tell this
render's version from the last one. The callback each page hands to its rows was
replaced on every edit, so one change re-rendered everything around it. And
reading the configuration at the root of the application meant a single flicked
switch re-rendered the library and the instance view behind the dialogue.

**Choosing an accent colour is smooth.** Dragging across the colour pad wrote
the whole preferences object to storage on every frame — a blocking write
between every two frames of the live preview it exists to feed. The preview is
still immediate; only the record of it waits for the drag to stop.

**The settings file cannot be left half written.** Moving the write off the main
thread meant two of them could genuinely overlap for the first time, and an
overlapping write leaves a file that will not parse — which reads as every
setting silently back to its default. Writes are now serialised and land by
rename, which cannot be caught half done.

## Changed

**The Mods page has the instance header, like every other page.** It was the one
page without it: no Play button, no instance name, no Sync — on the page most
time is spent on. Leaving Mods to launch the very instance being edited was not
a decision anyone had made on purpose.

**A mod's catalogue is shown with its logo.** CurseForge and Modrinth were
written out in words, in two colours belonging to neither: CurseForge came out
violet, which is closer to Modrinth's own colour than to its own. Each now
carries its real mark on its own filled colour — CurseForge's orange, Modrinth's
green — so a long list can be scanned instead of read. Content installed from a
file keeps its own description rather than being filed under a catalogue it
never came from.
